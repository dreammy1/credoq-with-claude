Credoq Suite

Five interconnected WordPress plugins — one core engine plus four addons — that together form a booking, registration, and membership platform. This document is the single reference for how they fit together, what every admin toggle actually does, and where the codebase currently stands.

credoq-engine

Forms/booking builder, React widget, field-type registry, SMTP, notifications, audit log. Every addon boots through it.

What each edge means

Free/credit path (synchronous)

Widget submit → Ajax\Booking → Submission_Handler::process() (sanitize, recompute price, insert submission row inside a DB transaction) → each field's on_submission() fires in form order → Field_Event writes event_bookings + Seat_Map_Field confirms seats in seat_bookings → transaction commits → credoq_after_submission fires Submission_Notifier (bell + email).

WooCommerce path (asynchronous)

Same as above, but the booking/registration row is created as pending_payment and a WC cart item is added. Seats are confirmed immediately at submission (reserved through checkout) — WooCommerce::on_complete()/on_cancel() later fire credoq_event_booking_confirmed/_cancelled, which Events_Bridge uses as a defense-in-depth re-sync (idempotent).

Request Lifecycle — Seat-Mapped Event Registration

The full, verified end-to-end path for an Events + Seats registration, step by step.

  1. Admin connects a published seat plan to an event (Seats → Plan Builder → Connect to a service). connected_ids stores the event ID(s).
  2. Visitor opens the registration form. Events_Bridge::inject_widget_config() has already injected an {event_id → plan_id} map into the widget config via the credoq_widget_config filter.
  3. Visitor selects an event in the calendar field. React's SeatMapField resolves the plan live from that map and renders the map (AJAX credoq_seats_load_map).
  4. Clicking a seat fires credoq_seats_hold — a 5-minute hold row is written to seat_bookings, scoped by (plan_id, date, event_id).
  5. Visitor submits. Submission_Handler recomputes price via each field's price_contribution()/wc_contribution() — Field_Event asks the credoq_events_seat_overrides filter for the seat plan's real total and uses it in place of its own flat price × qty.
  6. Field_Event::on_submission() writes the event_bookings row (quantity = real seat count, not the calendar's qty stepper) and either confirms it immediately (free/credit) or creates a WC cart item (pending_payment).
  7. Seat_Map_Field::on_submission() resolves the event unambiguously from the submission payload and confirms the actual seats in seat_bookings, each with its own recomputed price.
  8. If paid: WooCommerce order completes → on_complete() flips the booking to confirmed and fires credoq_event_booking_confirmed (Events_Bridge re-syncs seats, idempotent). If cancelled/refunded/failed → on_cancel() fires credoq_event_booking_cancelled per booking row → seats release.
  9. credoq_after_submission fires regardless of payment outcome → bell notification + admin email.

Appointments + Seats — Full Lifecycle

The reference-standard integration in the suite — Events + Seats was built to match this. Appointments uses its own bespoke booking pipeline, not the generic Forms Builder submission path Events relies on.

Request lifecycle, step by step

  1. Visitor picks a service. If show_staff_selector is on, they pick a staff member (or the widget auto-assigns one); each staff member's own price_multiplier applies to the service's base price.
  2. Slot_Generator resolves available times for the chosen date by checking, in priority order: (1) the staff member's own special_dates entry for that exact date (fully closed, or custom hours/price for that date) — (2) the staff member's recurring weekly hours (avail_{day}_enabled + hours) — (3) the service's own weekly hours as a fallback. The first layer that has an explicit answer wins; a later layer never silently overrides an earlier one's "closed" (an important fix — an empty array and a genuinely unset day are treated differently, not conflated).
  3. If allow_multi_booking is enabled, the visitor can select several sessions/dates in one submission; multi_price_mode decides whether the total is Per Session (base price × session count) or a flat Fixed Day Rate regardless of count.
  4. If the service has visual_seats_enabled and a connected published seat plan, the plain quantity control is replaced by the seat map (same credoq_seats_load_map/hold/release/get_booked AJAX used everywhere else in the suite). Seat availability is checked per staff + date + time, not just per date — two different staff members' concurrent bookings on a shared seat plan don't collide with each other's holds.
  5. Widget submits via Ajax\Booking_Handler.php — not the Engine's generic Submission_Handler. This is a deliberately separate, bespoke pipeline.
  6. Booking_Service::create() re-checks capacity (capacity_mode: Per Staff gives each staff member independent capacity per slot; Shared Pool draws all staff from one shared capacity_value) — using the seat plan's real seat count as the ceiling when one is connected, exactly like Events.
  7. Three-way credit decision (identical rule to Events' Field_Event::decide_payment()): (a) credit-enabled + sufficient balance on the customer's selected plan → confirm instantly, deduct credits, no WooCommerce involved at all; (b) credit-enabled but insufficient balance → falls through to WooCommerce checkout for cash payment; (c) credit-enabled but no membership plan available to the customer → a clear error, not a silent fallback.
  8. Booking row inserted into credoq_bookings. Seats — if any were selected — are held via the interactive click-to-hold flow already, and get upgraded to confirmed at this point via Appointments_Bridge::on_confirm(), using each seat's own individually recomputed price (never an average).
  9. Paid path: WC cart item added, order created as pending_payment; WooCommerce::on_complete()/on_cancel() mirror the confirmed/cancelled transitions and correctly restore/release seats and pricing on refund or failure.

Slot & capacity mechanics — how seat availability intersects with scheduling

Per Staff capacity mode

Each staff member's own slots are capacity-limited independently. If a seat plan is connected, each staff member's occurrence of that slot (same plan, same date, same time, different staff) is tracked as a distinct seat-booking scope — booking seat #4 for Dr. Smith's 2pm slot does not consume seat #4 for Dr. Lee's 2pm slot on the same date, even though both draw from the same physical seat plan.

Shared Pool capacity mode

All staff assigned to a slot draw from one shared capacity number for that date/time — matches a single-room/single-resource scenario (e.g. one consultation room, multiple practitioners rotating through it). The seat plan's physical seat count, when connected, is the real ceiling regardless of how many staff are nominally assigned.

Credoq Engine — Core Lifecycle

The foundation every addon builds on. Nothing below is addon-specific — this is what every submission, of any type, passes through.

Field-type registry

Addons register their field types (e.g. seat_map, event_registration, membership_credit) via the credoq_engine_ready hook into the Engine's Fields\Registry. Each field type is a class extending Abstracts\Field_Type, implementing sanitize(), validate(), price_contribution(), wc_contribution(), credit_cost(), and on_submission(). Registry::builder_descriptors() exposes each type's palette icon/label to the Forms Builder — this is metadata for building the drag-and-drop field list, not the settings-panel rendering (that's separately wired per field type, see the Settings Matrix's Forms Builder panel note).

React widget initialization

main.jsx mounts BookingWidget.jsx into each [credoq_booking_form]/[credoq_form] shortcode instance on the page. On mount, it fetches the form's config (fields, pricing rules, addon-injected extras like event_seat_plans via the credoq_widget_config filter) and renders the field list through FormField.jsx's per-type switch, falling through to a generic addon renderer driven by each field type's _frontend descriptor for anything without a hardcoded case.

AJAX submit pipeline

Two distinct paths exist, and they are not interchangeable:

  • Admin-ajax (standalone/non-appointment forms): useAjax.js's submitBooking(formData, false) posts real multipart FormData to admin-ajax.php?action=credoq_submit_booking, handled by Ajax\Booking.php. PHP parses bracket-notation nested fields (e.g. seat_map[seats][]) natively — no client-side reconstruction needed. recursive_sanitize() handles arbitrary nesting correctly.
  • REST (appointment-flow forms): submitBooking(formData, true) posts JSON to the REST /bookings endpoint instead. This path needed its own bracket-path parser fix (a historical bug where nested object values got mangled into flat garbage keys) — already fixed and verified not to affect the admin-ajax path, which never had the bug in the first place.

Submission_Handler transaction safety

Runs the whole submission inside one DB transaction: sanitize every field → compute total_price/total_credits/wc_items by summing each field's price_contribution()/credit_cost()/wc_contribution() → insert the submission row → fire each field's on_submission() in form order. If any field's on_submission() returns a WP_Error (e.g. an ambiguous seat-map event resolution), the whole transaction rolls back — nothing partially commits. Only after a successful commit does credoq_after_submission fire.

SMTP routing & notifications

Outgoing mail routes through either WordPress's default wp_mail() or a configured SMTP host (Settings → SMTP), independent of which addon triggered the email. Mail\Submission_Notifier hooks the generic credoq_after_submission action, so every submission — regardless of which addon's fields it contains — gets a bell notification and (if notify_on_submission is on) an admin email with zero addon-specific wiring required. This is why Events registrations get notified automatically while Appointments (which bypasses this generic pipeline entirely) needed its own dedicated notify hook.

Credoq Membership — Complete Lifecycle

Plan creation & restriction rules

Admin creates a plan (Membership → Plans) with a slot_credit allowance, optional allowed_form_ids scope, purchase_limit_expiry (blocks repurchase while a membership is still active), and optional qr_scan_enabled. Content restriction is configured per plan: restricted_pages[], restricted_products[], and restricted_urls gate access — non-members are blocked per the plan's restriction_html message or redirected via unlock_url. hide_css_selectors offers a softer alternative: hide specific page elements from non-members rather than blocking the whole page.

Credit ledger mechanics

Membership_Service is the single source of truth for every credit-consuming addon:

  • get_balance($user_id, $plan_id = 0, $form_id = 0) — the core read. $plan_id = 0 pools the balance across every active plan the user holds; a non-zero $plan_id scopes to just that plan. $form_id, when set, checks that plan's allowed_form_ids restriction.
  • get_plan_status($user_id, $plan_id, $form_id = 0) — a convenience wrapper returning {remaining, plan_id, user_id}, used by every addon's pre-flight sufficiency check.
  • deduct_credit() / refund_credit() — write ledger entries (type use/refund) against a specific plan. Every addon's cancellation path calls refund_credit() to reverse a prior deduction.
  • grant_membership($user_id, $plan_id, $order_id, $wc_status) — called on a successful plan-purchase WC order, sets the purchase/expiry dates and inserts the credoq_user_memberships row.

Every credit-consuming addon (Events, Appointments) follows the same three-way pattern against this ledger: check get_plan_status() before committing to the credit path, deduct on confirmation, refund on cancellation — see the Appointments + Seats and Events lifecycles above for the exact decision tree.

QR check-in

qr_scan_enabled on a plan is the data flag a dedicated QR Check-in addon would consume to generate and scan member badges at an event/venue door. As of this documentation, that addon is planned but not yet built — the flag exists on the Plans schema, but there is currently no scanning UI or verification endpoint shipping in the suite. Treat any "QR check-in" business use case below as a near-term roadmap item, not a shipping feature.

Unified 5-Plugin Ecosystem

How all five plugins coexist on one site without hard dependencies on each other.

The rule: soft dependencies only

Every addon checks class_exists('\CredoqX\...') before calling into another plugin's code, and every cross-plugin integration point is a WordPress filter or action (credoq_widget_config, credoq_events_seat_overrides, credoq_event_booking_confirmed/_cancelled, credoq_after_submission). Deactivating Seats, Membership, or any single addon degrades that one integration gracefully — the rest of the suite keeps working. Only Engine is a hard dependency, for all four addons.

Bridges — one per integration pair

Cross-cutting logic lives in small dedicated bridge classes owned by the "consuming" side of the integration, not scattered across both plugins: Seats\Integrations\Events_Bridge, Seats\Integrations\Appointments_Bridge. This keeps Events and Appointments free of any Seats-specific code beyond a handful of class_exists()-guarded calls and filter invocations.

Spending a membership credit on a seat-mapped Event or Appointment — the unified flow

This is the single flow that exercises all relevant parts of the ecosystem at once (minus Membership's own plan-purchase flow, which happens earlier/separately):

  1. Visitor is logged in with an active membership plan carrying spare credit (granted earlier via a WC purchase → Membership_Service::grant_membership()).
  2. They open a registration form (Events) or booking widget (Appointments) for a credit-enabled, seat-mapped event/service. Engine renders the form; Seats injects the plan/event resolution config; the visitor picks their seat(s).
  3. On submit, the real per-seat total is recomputed (never trusted from the client) — this is the number credits get measured against, not a flat qty × price.
  4. Membership's three-way decision runs: sufficient credit on the visitor's plan → instant confirm, no WooCommerce redirect, deduct_credit() fires for exactly the seat-based amount; insufficient → WooCommerce checkout for the real seat total instead; no credit-capable plan at all → a clear error naming the problem, never a silent fallback to a wrong price.
  5. Seats confirm in Seats' own table immediately (the reservation act, independent of payment timing) via the same confirm_seats()/per-seat price_map logic used everywhere else in the suite.
  6. If the visitor later cancels: Membership refunds the credit, Seats releases the seat, and (for Events) the booking status updates — three independent, idempotent operations, each triggered off the same cancellation event, none of them assuming the others already ran.

Business Use Cases & Solution Mapping

1. Theaters & Venues — ticketed seat reservation

Plugins: Engine + Events + Seats + WooCommerce.

Setup: Build the venue's seating chart in Seats → Plan Builder (floors, seat types, per-type and per-seat pricing overrides). Create the show/event in Events with a WC product for ticket sales. Connect the plan to the event (Connect to a service). Build a registration form in the Forms Builder with an event_registration field and a seat_map field — auto-resolution handles the rest, or pin both explicitly via the seat_map field's settings panel if this plan ever serves more than one showing.

Result: Buyers pick exact seats, pay the real per-seat price (VIP/standard/override-aware) through WooCommerce, and the seat map reflects live availability across every simultaneous buyer.

2. Medical / Salon / Consultations — staff-allocated slot booking

Plugins: Engine + Appointments (+ Seats, optional, for a waiting-room-style seat/chair assignment).

Setup: Add staff (practitioners/stylists) with their weekly hours and any blackout special dates. Create services with duration and price; set capacity_mode to Per Staff for independent practitioner schedules. Enable show_staff_selector so clients pick their preferred provider, or leave it off for auto-assignment.

Result: Clients book a specific provider's open slot; Slot_Generator's layered availability (special dates → weekly hours → service fallback) keeps the calendar accurate without manual slot management.

3. Fitness Clubs & Co-Working Spaces — gated access, credit-based booking

Plugins: Engine + Membership + Appointments and/or Events.

Setup: Create membership tiers in Membership (e.g. "10 classes/month") with slot_credit set accordingly. Enable credit_deduct_enabled on each class/session service or event, with credit_deduct_amount set to how many credits one booking costs. Optionally restrict the booking page itself to active members via restricted_pages[].

Result: Members book classes against their monthly credit allowance with zero payment friction (case (a) of the three-way decision); non-members or members who've used their allowance are seamlessly offered pay-per-class checkout instead (case (b)) rather than being blocked outright.

4. Hybrid Enterprises — all 5 plugins simultaneously

Plugins: All five, concurrently, for different lines of business on one site.

Example: A performing-arts venue that also runs recurring workshops and a members' program. Events + Seats handles ticketed main-stage shows; Appointments (with its own optional seat integration) handles small-group workshop bookings with instructor assignment; Membership provides a "Friends of the Venue" tier granting discounted/credit-based access to both. Because every cross-plugin touchpoint is filter/hook-based rather than hard-wired, none of these three business lines interfere with each other's data or logic — they share only the Engine's form builder and submission plumbing.

Admin & Frontend Journeys

Admin setup journey (typical order, any subset of plugins)

  1. Install & activate Engine first, then whichever addons the business needs.
  2. Engine → Settings: set currency/date/time formats, SMTP, and security options (reCAPTCHA, IP/country blocking) once — shared by every addon.
  3. Per addon: create the underlying entities — Staff + Services (Appointments), Events (Events), Seat Plans (Seats), Membership Plans (Membership).
  4. If using Seats: connect plans to the events/services that need them (Plan Builder → Connect to a service) — do this before building forms that reference them, so auto-resolution and the settings-panel dropdowns have something to find.
  5. Build the registration/booking form in the Forms Builder, add the relevant fields, and place the shortcode on a page.
  6. Test the full frontend flow once as a guest and once as a logged-in user before going live — the two paths differ (see below).

Frontend user journeys

Guest checkout

No account required unless require_login is on. Name/email collected inline on the form. Credit-based payment is unavailable (credits are tied to a logged-in user's account) — guests always see the WooCommerce/cash path for priced bookings.

Logged-in, no membership credit

Identical to guest checkout for payment purposes, but the account's booking history is retained and tied to their user ID.

Logged-in, spending membership credit

See the unified credit-spend flow above — instant confirm with no WooCommerce redirect when sufficient credit exists, transparent fallback to payment when it doesn't.

Seat selection (any of the three above)

Click seats on the live map → 5-minute hold per seat → submit locks in the real seat-based price and count, overriding any quantity stepper elsewhere on the form.

Automated Test Suite

Shipped separately as credoq-test-suite.zip — a standalone, portable harness. No WordPress install or database required; pure PHP CLI.

Test architecture

Not PHPUnit — a lighter, purpose-built harness (tests/wp_stubs.php) providing a fake $wpdb and the minimal set of WordPress functions (apply_filters, sanitize_*, nonce/user stubs) these specific cross-plugin scenarios need. This was a deliberate choice: the bugs this suite exists to catch — missing methods, wrong hook arguments, averaged-instead-of-per-item prices, cross-entity ID collisions — only surface by actually executing the real plugin code path end to end, not from isolated unit assertions against mocked interfaces. Each tests/testN_*.php file requires bootstrap.php (defines a configurable PLUGINS_DIR) and the real plugin source files it needs, then runs a self-contained scenario and prints PASS/FAIL per assertion.

Execution guide

Local:

unzip credoq-test-suite.zip
export CREDOQ_PLUGINS_DIR=/path/to/plugin-checkouts
cd citest && ./run-all.sh

Plugin checkouts must sit side by side using their real folder names (credoq-engine-v3, credoq-appointments, credoq-events-v3, credoq-seats, credoq-membership-v3) inside that directory — or drop them in a plugins/ folder next to run-all.sh and skip the environment variable. Requires PHP 8.1+ CLI (the harness itself; the plugins under test remain PHP 7.4-compatible). run-all.sh exits non-zero if any test file fails, so it's ready to wire into a CI job as-is.

CI (GitHub Actions example):

- uses: actions/checkout@v4
- uses: shivammathur/setup-php@v2
  with: { php-version: '8.1' }
- run: |
    mkdir plugins
    # checkout/copy each plugin repo into plugins/<real-folder-name>
    cd credoq-test-suite/citest
    CREDOQ_PLUGINS_DIR=$PWD/../../plugins ./run-all.sh

Note: this documentation package doesn't include a live GitHub repository or Actions workflow file — the suite is delivered ready to drop into one. If/when repo access is provided, the workflow above is copy-paste-ready.

Adding a new test

Copy the shape of any existing testN_*.php: require bootstrap.php first, then wp_stubs.php, then only the specific plugin source files the scenario needs. These are intentionally narrow, fast, execution-based tests — not a full WordPress bootstrap — so keep new tests scoped to one real bug or behavior per file.

UI/UX Guidelines

  • Never let a customer-facing number silently disagree with what's charged. Any field that contributes to a live total must recompute server-side before payment — the frontend total is a preview, not a source of truth.
  • Fail loud, not silent, on ambiguity. When a seat map can't determine which event/service it belongs to, reject the submission with a clear message rather than guessing — a wrong guess here means a real customer's money goes to the wrong seat.
  • Toggle labels state the effect, not the mechanism. "Guests must be logged in to book" rather than "require_login = true" — every setting in the matrix above should read the same way in the admin UI.
  • Destructive bulk actions get their own opt-in checkbox. See Seats' "Also overwrite every existing seat's individual price override" — bulk pricing changes never touch manual overrides unless explicitly asked.
  • Only Published entities are selectable downstream. Draft seat plans, draft events, and draft services should never appear in another plugin's picker — consistent across Appointments and Events.
  • Same action, same word, every time. A booking that's "Confirmed" in the database should never be labelled "Approved" or "Active" in a different admin screen.
